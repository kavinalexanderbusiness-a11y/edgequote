## B1: versioned acceptance API, aliases and actual displayed choice

The future public application API is three dormant server functions with injected request/auth/store dependencies, not mounted Next routes:

```ts
previewQuoteAcceptance(request, auth, store): Promise<Response>
commitQuoteAcceptance(request, auth, store): Promise<Response>
reconcileQuoteAcceptance(request, auth, store): Promise<Response>
```

POST JSON only, no-store, bounded body, same-origin for owner/session requests. The portal token is a bearer authority supplied in the request body, never a log or URL generated by the new API. The owner door derives owner from getUser. No owner ID or actor label is accepted from a client. The server calls one of these exact dormant service-only database signatures, fixed search_path with explicit revoked default execution:

```sql
pilot_quote_acceptance_preview(p_owner uuid, p_portal_token text, p_quote uuid,
                              p_option uuid) returns jsonb;
pilot_quote_acceptance_commit(p_owner uuid, p_portal_token text, p_quote uuid,
                             p_expected jsonb, p_option uuid, p_addons uuid[],
                             p_reason text, p_note text, p_terms_ack boolean) returns jsonb;
pilot_quote_acceptance_reconcile(p_owner uuid, p_portal_token text, p_quote uuid,
                                p_expected jsonb, p_option uuid, p_addons uuid[],
                                p_reason text, p_note text) returns jsonb;
```

Exactly one of p_owner/p_portal_token is nonnull. The service-only owner argument is supplied only after verified application auth; a mismatching nonnull auth.uid is refused. Portal token lookup resolves owner/customer inside SQL and repeats that resolution under lock. Both-null/both-nonnull is invalid. No forgery of JWT claims to impersonate owner. The preview is read-only: it neither calls choice nor creates an acceptance/config/receipt row.

Preview request keys: `{version:1, quoteId, optionId:null|string, portalToken?:string}`. Owner mode omits portalToken entirely. Commit adds exactly `{expected, addonIds, reason:null|string, note:null|string, termsAck:boolean, clientOperationId}`. Portal forbids reason/note; owner requires canonical reason and the existing explicit owner attestation. The owner door retains native on-behalf terms semantics (not a claim the customer ticked a portal box). Preview/commit correlation cannot be used as authorization.

**Displayed add-ons decision:** preview reads the exact currently selected add-on IDs, names and prices. The confirmation explicitly lists those included extras, displays their amount and submits that exact set. There is no new selector, no newly selected default and no inferred customer click. The confirmation itself is the explicit consent to that itemized offered document. If the person does not want those included extras they cancel; editing their selection remains the existing separate workflow. This repairs the current mismatch where the dialogs can include selected extras in total while omitted p_addon_ids means native empty-set deselection. Coordinator was notified of this concrete correction before implementation. Any contrary product decision holds this part; no silent fallback to an empty set.

Preview includes exact offered option/services/add-ons and pricing inputs for the existing confirmation formatter. Explicitly extract the existing native amount expression into one private immutable `quote_choice_amount(p_base numeric,p_travel numeric,p_addons numeric)` seam returning the existing coalesced sum. Patch the exact pinned amount expressions in both quote_apply_choice and quote_record_acceptance to call it, and have preview call that same seam after resolving the option/base and selected add-on sum through the quote. This shared extraction is authorized in addition to the core row-count patch described below; it changes neither the no-charge/choice/terms gate nor rounding/column types. Prove old-expression and new native results equal for normal, null, zero, option, travel and add-on cases. Do not derive acceptance by mutating then rolling back a real quote. No recommendation or fee recovery reruns. The actual portal and owner callers render **only this preview** for the confirmation and send **its exact precondition**, held immutable while the dialog is open. Changing a choice requests another preview before confirming; it never silently advances the old precondition after confirmation. Terms acknowledgement is reset if displayed terms change.

### Finite preview revision recipe

The server produces `expected = {version:1, quoteId, previewRevision, priorAcceptanceId, priorAcceptanceSeq, offered}`. `offered = {public: confirmationProjection, authorityFence: opaqueDigest}` is immutable. Only explicitly whitelisted customer-visible confirmation fields enter public. The actual caller retains it from the preview without replacing it after confirmation. IDs are not authority. `previewRevision = md5(offered::jsonb::text)`, computed inside SQL over deterministic canonical JSON. It is an equality fence, not a signature or a security secret; commit rebuilds the full offered projection and authorityFence from authorized rows under locks and requires equality to both supplied projection and digest. All arrays order by sort_order,id. The expected object contains no arbitrary rows or SQL patch. Strict shape/size validation applies to the offered projection too.

The complete internal preview hash input binds the following exact keys. This is an internal dependency inventory, **not a public payload allowlist**:

- `owner_id`, `quote_id`, `customer_id`, `property_id`, `customer_name`, `actor_customer_name` (for portal ledger label), `quote_number`.
- `status`, `valid_until`, `sent_at`, current `selected_option_id`; exact no_charge_at/reason/by trio (authority to accept zero). Null remains null; no missing→empty normalization except inside existing canonical fingerprints.
- `material_fingerprint = quote_material_fingerprint(quote_id)` and `terms_fingerprint = quote_terms_fingerprint(owner_id)`.
- Quote display/pricing fields: raw initial_price, travel_fee, addons_total, generated total, weekly_price, biweekly_price, monthly_price, deposit_type/value, service_type, address and public notes. Retain raw null/empty distinctions in preview even when canonical standing normalizes them.
- Ordered option public records: id, name, description, price, sort_order, is_recommended; ordered service public records: id, service_type, quantity, unit, unit_price, est_minutes, discount_type/value, notes, kind, sort_order. No internal notes in portal projection.
- Ordered add-on public records: id, name, price, is_selected, sort_order. The chosen option ID and exact sorted selected add-on IDs are also hashed explicitly. Selection provenance timestamps are authority/internal checks, not displayed customer content.
- Settings existence; exact terms_text, terms_payment_claim/fingerprint/version, gst_percent, owner_name/company_name needed for the existing owner actor label. These are separate fields because quote_terms_fingerprint hashes only trimmed terms text, not classification/tax/label. No booking/payment/provider credentials or unrelated settings.
- Latest acceptance ID/seq and canonical quote_acceptance_is_current result. Existing standing remains native, not recomputed from this preview token.
- Portal-only token identity/binding/revoked state, hashed internally; raw token never appears in returned expected or logged evidence. Token row plus matching customer must exist and remain locked through commit. Owner mode has a null token binding.

Public confirmationProjection contains only quote_id, customer_name, quote_number, public address/service_type/notes, current status/valid_until, initial/travel/add-on/generated/recurrence prices, deposit_type/value, selected option ID, public ordered option/service/add-on fields listed above, exact included add-on IDs, terms_text, gst_percent and displayed company_name. It may include a derived boolean that a no-charge declaration exists, but never its reason/author/timestamp. The server's authorityFence hashes the remaining nonpublic dependencies: owner/customer/property linkage and actor label source, raw no-charge trio, terms classification fields, settings existence, token binding and any internal authority state. Existing public data must not expand to include raw no_charge_reason/no_charge_by, terms_payment_claim/fingerprint/version, internal notes, credentials or raw token. The native material/terms equality results and prior acceptance preconditions may remain opaque alongside the projection; their digests are not a new public evidence endpoint.

On reconciliation, compare the current internal authorityFence to the preview's supplied digest, with only the explicitly modeled acceptance transition excluded from the stable fence; if any unrecorded historical authority dependency cannot be established, return unknown. Do not try to reconstruct undisclosed internal values from a client-supplied object or expose them to make reconciliation easier. Status/choice/price and previous→new acceptance sequence are validated separately against the authoritative ledger as described below.

Canonical material fingerprint includes normalized primary/travel/add-on/recurrence prices; deposit; trimmed service/address/public notes; selected option; ordered service commercial rows; ordered option IDs/names/descriptions/prices; ordered add-on IDs/names/prices/is_selected. It deliberately excludes internal_notes, measurements, property/customer repairs, follow-up/scheduling fields. It also does not independently bind quote_number, validity/sent dates, no-charge declaration, raw public formatting, GST, terms classification or token authority. Those needed for confirmation are explicitly covered above. **No change to what the native standing engine calls a material revision.**

Expiry: preserve the current UI's `displayQuoteStatus(..., localTodayISO())` check before confirmation and repeat it immediately before submitting, using the preview's bound valid_until. The native door currently does not impose a tenant-timezone expiry rule. This companion binds validity-date changes; it does not silently introduce a different backend calendar policy. A server-enforced expiry/timezone policy is an explicit further gate if requested, not part of the current-document-version claim. Do not describe the preview token as solving midnight/incorrect-browser-clock expiry authority.

## B2: supported writer and absence fences

Shared order for **new Save and versioned acceptance** is: pilot owner advisory → owner `auth.users` row FOR UPDATE → customer rows sorted UUID → property rows sorted UUID → quote FOR UPDATE → quote_options sorted UUID → quote_services sorted UUID → quote_addons sorted UUID → service_templates sorted UUID → business_settings row → quote_acceptances sorted UUID → property_measurements sorted UUID → applicable existing portal-token row. Resolve candidate IDs with an initial nonauthorizing read, then reacquire/revalidate all after locks. A changed/missing/rebound identity refuses; no lock acquired on a guessed foreign tenant after authorization mismatch. Lock only synthetic account rows in native proof; no production auth reads/writes are part of this task.

The additional auth.users row lock is a **row fence, not an auth mutation**. It blocks new owner-bound rows through nondeferrable native FK KEY SHARE, including a settings row that was absent at preview. The actual baseline `business_settings_user_id_fkey` at8354, portal token user FK8391, measurement user FK8516 and quote child/acceptance user FKs8540–8549 reference auth.users(id) without DEFERRABLE. Native proof must confirm confdeferrable=false and observe this wait; do not claim the owner advisory alone does this. Existing row edits are separately locked below. This adds owner-scoped contention; no global table lock or throughput claim. Any native lock-order inversion must abort completely or be an explicit unsupported integration blocker.

| Writer/state | Existing source path / fence | Supported outcome |
| --- | --- | --- |
| Quote parent edits/status/no-charge/delete | Direct owner DML and quote status/no-charge/override functions; quote FOR UPDATE blocks row mutation | After wait compare full Save tuple/content baseline; acceptance compares explicit preview fields and eligibility. A status-only override records no consent |
| Existing options/services/add-ons update/delete | Direct native owner DML; lock every current child row, then repeat ordered complete-set read | No missed row after wait; stale intent refused. Native child→quote trigger inversions may deadlock/rollback |
| New or reparented quote children | Native quote/user FK checks: quote FOR UPDATE and auth.users FOR UPDATE conflict with needed FK locks | Confirm native constraints are validated/nondeferrable; no omission of empty-set insertion case |
| Existing settings update/delete | business_settings row lock prevents terms/classification/GST/price input change during comparison and record | Source formula remains canonical; stale preview refuses |
| Previously absent settings inserted | Owner auth.users FOR UPDATE fences user FK insert; re-read presence after lock | Known absence can remain absence; no new requirement that an unchanged-price Save invent settings |
| Existing customer/property edits/archive/delete | Sorted customer/property row locks and PR121 checks | Native deletion/archive/measurement order inversion is allowed only as whole-operation abort |
| New customer/property/resolver candidate | Owner auth.users and relevant customer FOR UPDATE fence actual FK inserts; re-read complete canonical candidate sets | Prove these exact FKs; no global dedup claim for writers that disable/bypass native constraints |
| Existing typed measurement upsert/delete | Property then typed measurement lock plus complete value/source/shape/meta compare | Concurrent measurement-first mirror writer can deadlock; loser rolls back, no retry loop |

Same-owner Save→Save serializes on owner advisory; the owner row fence also serializes many ordinary owner inserts. In the cloud measure wait behavior, not performance. Keep locks short: no remote calls, human confirmation, sleep or network retry inside database transaction.

The full q JSON and internal rows stay server-only; browser receives explicit editor fields and opaque revision. Add per-row xmin to child/template records in the internal baseline so delete/reinsert or identical update cannot silently adopt a stale intent. Known absence is JSON null, never omitted key or failed read. xmin is a live tuple version; a maintenance rewrite may safely cause extra stale refusals, and it is not a forever-global ID or durable receipt.

Do not pretend target lawn dependencies exist in that initial token. The Save server performs a **read-only planning/rebind** using the original expectedEditorRevision and submitted identity/template inputs, runs the actual resolver facade, then fetches exact resolved target-property/typed-measurement/template dependencies. That planning call returns no customer/property INSERT; new targets use planned UUIDs and explicit absence. If the original base revision differs, refuse; never update it to today's quote to make a draft fit. The server keeps this newly built plan private and immediately sends the full transaction, which checks the original editor revision **and** target dependency revision under the shared locks.

The target revision binds complete typed measurement with xmin or null; property mirror/lawn/owner/customer/full property revision; target customer projection/revision; relevant templates and changed-price settings. Resolver candidate caps/order remain PR121's. Rebinding happens once per explicit Save, not in an automatic retry. A target/template/input change during planning cancels the current UI generation; its late response cannot be used for a different form. These are transport/resource guards, not new service-count/business limits. The native suite includes exact bound and just-over-bound refusals, with no sensitive payload printed.

## B4: opt-in draft recovery, current form and acknowledgement

Add a **dormant opt-in quote-save controller**, not new default behavior for every useAutosave caller. It uses the existing verified-owner cache lease. Add optional builder/hook integration surfaces needed for this controller; default remains byte-equivalent. The new edit path explicitly opts into verified-owner storage; it never imports, deletes or assigns an old unowned legacy draft to the current owner.

The controller stores a unique immutable pending record per owner/quote/operation, independent of the ordinary autosave slot:

```ts
type PendingQuoteSave = {
  version: 1; owner: string; quoteId: string; clientOperationId: string;
  editorGeneration: string; originalEditorRevision: string;
  submittedValues: QuoteFormValues; submittedSerialization: string;
  stagedAt: number; state: 'pending' | 'unknown';
};
```

The pending key includes verified owner, quote and unique operation ID. There is no timestamp-based eviction for unresolved records; normal explicit successful resolution/discard semantics apply, no new server-retention policy. No key/cookie/provider secret is stored. It is recovery content, never a credential or server precondition authority.

Before network dispatch: verify current lease+generation, cancel the obsolete autosave timer, synchronously serialize and write the submitted snapshot plus pending record, read it back exactly, then dispatch once. If storage is unavailable/quota-full/readback fails, **refuse before dispatch**, keep the form visible and say a recovery copy could not be saved; no cross-reload durability claim. Ordinary typing remains usable. The controller cannot call a flush API that does not exist: implement a narrow opt-in synchronous `stageSubmission`/`clearSubmissionIfCurrent` hook seam and test it with the actual builder lifecycle.

The current editable values remain a separate autosave value. While any unresolved pending record exists for this verified owner+quote, the opt-in recovery path must not delete the current draft merely because server updated_at is newer. Check pending records before rendering/enabling the hook's recovery effect. It may show a draft alongside newer saved values for review, but never automatically restore over or submit against that newer server revision. Newer edits during a request are flushed on the opt-in lifecycle's exit/unmount while the lease is valid; a lost lease prevents cross-account storage access and makes no recovery promise for unsaved keystrokes after logout.

At successful acknowledgement, compare owner lease, quote, generation and current form serialization to the submitted snapshot **inside the builder submit/clear boundary after the await**. If any differs, retain current form/draft; remove only this operation's pending record after storing its committed result for same-owner reconciliation, without clearing newer work. The ordinary builder `onSubmit !== false` path must be bypassed for this opt-in controller; its result is not a bare boolean that can clear a different draft. Conditional clear cancels stale timers and removes only the exact owned draft revision/generation. No unknown or malformed receipt enters that path.

At failed acknowledgement keep both immutable submitted snapshot and current editable draft; mark pending record unknown. On owner-bound reopen, unresolved recovery is offered even when the server is newer. Read-only reconciliation can identify matching saved values or conflict, but cannot prove which request committed. The user can keep current saved data, keep/review their draft, or explicitly discard that recovery entry; no automatic retry or remapping of old values to a new revision. Existing pending operations from another owner are not read or rendered. No assumption that localStorage provides cross-tab compare-and-swap: unique operation records never clear another operation; conditional ordinary-draft writes/clears must use a generation-aware storage seam and native Web Locks when multiple tabs share the same key, or use per-editor-instance draft keys for this opt-in flow. **Choose per-editor-instance keys** here to avoid introducing a cross-tab lock dependency; list unresolved same-owner/quote instances only on explicit recovery, and never overwrite one instance from another.

Implementation tests include successful commit/lost response/server-newer reopen, storage denied/quota full before write, account switch, pendingCancel/reopen, two editor instances, newer typing during pending request, obsolete timer flush/clear, a corrupt/foreign recovery entry, and matching server data that cannot be attributed to this request. Browser tests must exercise the actual opt-in builder/hook seam, not only a pure result mapper.
